# 项目2（组件编译篇）：box64 交叉编译与升级 0.4.0 → 0.4.3

> 本篇记录把二进制翻译核心组件 box64 从 winlator 内置的 0.4.0 升级到上游最新 v0.4.3-3 的完整过程，包括交叉编译环境、命令、遇到的问题与解决、集成与验证。这是项目2"编译各组件并升级到最新版"的第一个落地组件。

## 一、为什么先做 box64

见 [[项目2-组件版本基线与升级评估]]：box64 是几个组件里编译最简单的（纯 CMake + Android NDK，无需 MinGW/meson），且当前 0.4.0 与上游 0.4.3-3 差距不大，适合先验证交叉编译流程。

## 二、编译环境

| 工具 | 版本/路径 |
|---|---|
| Android NDK | r24 (24.0.8215888)，`aarch64-linux-android31-clang` |
| CMake | 3.22.1（随 Android SDK） + ninja |
| 源码 | ptitSeb/box64，tag **v0.4.3-3**（commit e2345d7） |
| 目标 | arm64-v8a / android-31 |

## 三、编译步骤

### 1. 拉取源码
```bash
git clone --depth 1 --branch v0.4.3-3 https://github.com/ptitSeb/box64
```

### 2. CMake 配置（参考 box64 官方 release.yml 的 ANDROID 平台）
```bash
cmake -S box64_src -B build_android -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=<NDK>/build/cmake/android.toolchain.cmake \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-31 \
  -DANDROID=1 -DARM_DYNAREC=1 -DBAD_SIGNAL=1 \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo
```
关键参数：`-DANDROID=1`（Android 平台）、`-DARM_DYNAREC=1`（开启 ARM64 动态重编译，box64 性能核心）、`-DBAD_SIGNAL=1`（Android 内核信号处理兼容）。

### 3. 编译
```bash
cmake --build build_android -j6
```

## 四、遇到的问题与解决

### 问题：`git_head.h` 生成失败导致 ninja 中断（Windows 特有）
编译进行到 223/577 时报错：
```
[223/577] Generating ../src/git_head.h
FAILED: ../src/git_head.h
cmd.exe /C "... sh -c "echo \#define GITREV ... $(git rev-parse --short HEAD)..."
'sh' is not recognized as an internal or external command
ninja: build stopped: subcommand failed.
```
**根因**：box64 用一条 `sh -c "…git rev-parse…"` 的规则生成记录版本号的 `git_head.h`。在 Windows 的 `cmd.exe` 下 `sh` 不在 PATH，该步骤失败，ninja 随即停止。与 box64 代码无关，纯 Windows 环境问题。

**解决**：把 Git for Windows 自带的 `sh.exe`（`D:\software\Git\usr\bin`）加入 PATH 后续编：
```powershell
$env:PATH = "D:\software\Git\usr\bin;D:\software\Git\cmd;<cmake bin>;$env:PATH"
cmake --build build_android -j6
```
ninja 复用已编译的对象，仅补 `git_head.h`（正确生成 `#define GITREV "e2345d7"`）及剩余部分，最终 `[351/351] Linking C executable box64` 成功。

## 六、strip 与打包

用 NDK 的 `llvm-strip --strip-unneeded` 去符号：
- strip 前 **69.0 MB** → strip 后 **21.8 MB**。

按原 `box64-0.4.0.tzst` 的目录结构（`./usr/local/bin/box64`，权限 0755）用 zstd(level 19) 打包成 `box64-0.4.3.tzst`（**3.21 MB**，比原 0.4.0 的 3.87MB 略小）。

## 七、集成到 winlator

1. 新 tzst 放入 `app/src/main/assets/box64/box64-0.4.3.tzst`，删除旧 `box64-0.4.0.tzst`。
2. 改 `app/src/main/java/com/winlator/core/DefaultVersion.java`：`BOX64 = "0.4.0"` → `"0.4.3"`。
3. 确认无其它硬编码 "0.4.0" 引用（grep 验证）。
4. 运行时逻辑：`GuestProgramLauncherComponent.extractBox64File()` 按 `DefaultVersion.BOX64` 找 assets 里的 `box64-<版本>.tzst` 解压到 `<root>/usr/local/bin/box64`；版本变化时会重新解压（`current_box64_version` 比对）。

## 八、验证与踩坑复盘（重要）

### 首次尝试失败：编错目标导致启动容器闪退
第一版用 **Android NDK（`-DANDROID=1`，Bionic 目标）** 编译，APK 能装，但**启动容器立即闪退**。日志：
```
CANNOT LINK EXECUTABLE ".../usr/local/bin/box64":
  ".../usr/lib/libc.so" has bad ELF magic: 2f2a2047
```
**根因分析**：
- `bad ELF magic: 2f2a2047` = ASCII `/* G`，说明加载的"libc.so"其实是一段以 `/* GNU ld script */` 开头的**链接脚本文本**，不是 ELF。
- 对比依赖：
  - 原版 0.4.0（可用）：NEEDED `libc.so.6`、`ld-linux-aarch64.so.1`（**glibc 命名**），且 RUNPATH=`/data/data/com.winlator/files/rootfs/lib`，interpreter=`/data/data/com.winlator/files/rootfs/lib/ld-linux-aarch64.so.1`。
  - 我编的 0.4.3（闪退）：NEEDED `libc.so`、`libm.so`、`libdl.so`（**Android/Bionic 命名**），无 RUNPATH。
- winlator 跑的是 **glibc rootfs**（项目2 架构篇已述：无 proot、glibc 环境）。Bionic 目标的 box64 去 `LD_LIBRARY_PATH=<root>/usr/lib` 找 `libc.so`，命中 glibc 的 ld 脚本文本，链接失败。

**正确做法**：必须按 box64 CI 的 **`ANDROID_GLIBC`** 平台编：
```
编译器: aarch64-linux-gnu-gcc  (glibc 交叉编译器，非 NDK)
cmake:  -DARM64=1 -DWINLATOR_GLIBC=1 -DARM_DYNAREC=1 -DBAD_SIGNAL=1
编后:   patchelf --set-interpreter /data/data/com.winlator/files/rootfs/lib/ld-linux-aarch64.so.1 box64
```
> 注意 box64 CI 打包脚本里写的是 `imagefs` 路径，但本 fork 的 rootfs 目录名是 **`rootfs`**，故 interpreter/RUNPATH 要用 `.../files/rootfs/lib`（与原版 0.4.0 一致）。

**Windows 障碍**：`aarch64-linux-gnu-gcc` 是 Linux 原生工具链，Windows 装不了 → 改用 **Docker Linux 容器**编译（见下一篇文档）。

### 临时回滚
为恢复可用，已把 box64 退回 0.4.0（`DefaultVersion.BOX64="0.4.0"` + 恢复 `box64-0.4.0.tzst`），APK 重编验证通过。0.4.3 待用正确的 ANDROID_GLIBC 方式重编后再上。

### 第二次尝试：ANDROID_GLIBC 目标——编译成功但真机 SIGSEGV（未解决）
用 **WSL Ubuntu 22.04 + `aarch64-linux-gnu-gcc` 11.4** 按 ANDROID_GLIBC 正确重编：
```
cmake .. -DCMAKE_C_COMPILER=aarch64-linux-gnu-gcc \
  -DARM64=1 -DWINLATOR_GLIBC=1 -DARM_DYNAREC=1 -DBAD_SIGNAL=1 -DCMAKE_BUILD_TYPE=RelWithDebInfo
make -j$(nproc)
patchelf --set-interpreter /data/data/com.winlator/files/rootfs/lib/ld-linux-aarch64.so.1 box64
patchelf --set-rpath /data/data/com.winlator/files/rootfs/lib box64
aarch64-linux-gnu-strip --strip-unneeded box64
```
**静态验证全部正确**（与能跑的 0.4.0 一致）：NEEDED=`libc.so.6`/`ld-linux-aarch64.so.1`（glibc）、interpreter/RUNPATH 指向 `rootfs/lib`、ELF 类型 EXEC 固定加载地址、所需 GLIBC 符号仅 2.35（低于 0.4.0 的 2.39，不是符号问题）。

**但真机仍启动容器闪退**。逐步诊断：
1. 加"退出信号"日志（绕过 debug callback 门控，进程结束必写一行）→ 得到 `killed by SIGSEGV (exit 139)`，且崩溃前 box64 零输出。
2. 强制开 `BOX64_LOG=1 BOX64_SHOWSEGV=1 BOX64_SHOWBT=1`（让 box64 从最早期 verbose + 崩溃打印堆栈）→ 日志**仍零 box64 输出**。

**结论**：box64 0.4.3 在 `main()` 之前的**极早期启动阶段**（box64 在固定地址 0x34800000 预留内存区的阶段）就 SIGSEGV，连 banner 都来不及打，拿不到任何堆栈。已排除：glibc 符号版本、动态依赖、ELF 类型、interpreter/RUNPATH。最可能是 **WSL 通用工具链编出的固定内存布局/早期启动代码与本设备不兼容**——box64 官方给 Winlator 的构建使用特定构建环境和**设备专属编译选项**（CMakeLists 里有 SD845/865/888/8G2/8EG5 等骁龙各代选项 + 16KB 页相关），通用 `-DARM64=1` 未针对具体芯片。

**决策**：box64 0.4.0→0.4.3 属小版本、收益有限，而精确定位需设备 tombstone（需 root/adb）或逐一试设备专属选项（每轮都要真机测），投入产出比低。**暂缓 box64 升级，保持可用的 0.4.0**，优先做收益更大的 DXVK 升级。此段完整踩坑记录即为项目2"整理编译中出现的问题"的一手材料。

## 九、复用到其它组件的教训

- **交叉编译最关键的是"目标 ABI/libc 要与运行环境一致"**：winlator = glibc rootfs，所有原生组件都要编成 **glibc 目标**（`aarch64-linux-gnu`），不是 Android/Bionic（NDK）。这次的教训是把二者搞混了。
- box64 的 `ANDROID`（Bionic）与 `ANDROID_GLIBC` 是两个不同平台，winlator 用后者。
- DXVK/VKD3D 是 Windows DLL，需 **MinGW-w64 + meson**；Turnip/Zink 属 Mesa，需 meson + 复杂依赖。
- 各组件 tzst 内部结构不同（box64 是 `/usr/local/bin/`，图形驱动是 `/usr/lib/`），打包前先解开原包对照。

## 十、最终解决（推翻前面的"暂缓"结论）✅

前面第八节的"设备兼容/暂缓"结论是**错的**。继续排查后找到真正根因并成功升级到 **0.4.3**。

### 真正根因：多余的 patchelf --set-rpath 和 strip
深度对比"能跑的官方 0.4.0"与"我编的崩溃版"的 ELF，发现关键差异在**打包步骤**，不是版本、不是编译器、不是设备：
- 官方 box64 打包**只做** `patchelf --set-interpreter`，**从不** `--set-rpath`，**也不** `strip`。
- 我之前多做了 `--set-rpath` + `strip`。box64 是**非 PIE、固定加载地址 0x34800000** 的特殊二进制，用 patchelf 事后改 `--set-rpath` 会重写它的程序头/`.dynamic`，破坏这个不可重定位二进制的加载 → 在动态链接器阶段（`main()` 之前）就 SIGSEGV，所以 `BOX64_LOG=1` 也一个字打不出。
- rpath 本来就多余：winlator 启动 box64 时已设 `LD_LIBRARY_PATH=<root>/lib`，运行时能找到 libc。

（附：能跑的 0.4.0 的 RUNPATH 是**链接时**由 brunodev 的构建内建的，不是 patchelf 事后加的——两者对固定地址二进制的影响不同。）

### 正确配方（已验证 0.4.3-4 真机通过）
```
git clone --depth 1 --branch v0.4.3-4 https://github.com/ptitSeb/box64
cmake .. -DCMAKE_C_COMPILER=aarch64-linux-gnu-gcc \
  -DARM64=1 -DWINLATOR_GLIBC=1 -DARM_DYNAREC=1 -DBAD_SIGNAL=1 \
  -DTERMUX=0 -DBOX32=0 -DHAVE_TRACE=0 -DSTATICBUILD=0 -DCMAKE_BUILD_TYPE=Release
make -j$(nproc)
patchelf --set-interpreter /data/data/com.winlator/files/rootfs/lib/ld-linux-aarch64.so.1 box64
# 关键：不要 --set-rpath，不要 strip
```
按此打成 `box64-0.4.3.tzst`（4.52MB，未 strip），改 `DefaultVersion.BOX64=0.4.3`，重编 APK。

### 验证结果
真机安装后**正常进入桌面，星露谷正常打开**。box64 成功从 0.4.0 升级到最新 **0.4.3-4**。

### 核心教训（比失败本身更重要）
- **对非 PIE 固定地址二进制（box64/wine loader 等），不要用 patchelf 改 rpath、不要 strip**——只改 interpreter 是安全的。
- 排查"main 之前、无任何输出的 SIGSEGV"时，应优先怀疑**加载/打包阶段**（interpreter、rpath、strip、PIE），而不是程序逻辑。
- 定位方法：拿**能跑的官方产物**逐项 `readelf` 对比（interpreter/RUNPATH/是否strip/编译器.comment/ELF类型），差异项即嫌疑。
