## 详细总结一：项目2 Box64 升级卡点

### 背景与现象

项目2要把 Winlator 内置 Box64 从 0.4.0 升级到上游 v0.4.3-3。第一版 APK 能安装，但进入容器立即闪退，日志只留下：

```text
CANNOT LINK EXECUTABLE .../usr/local/bin/box64
.../usr/lib/libc.so has bad ELF magic: 2f2a2047
```

回滚到 0.4.0 后容器恢复，说明问题集中在新 Box64 产物或其集成方式，而不是游戏文件。

### 完整排查链

1. **先查 ABI，而不是猜代码逻辑。** 对 0.4.0 与失败版做 `file/readelf` 对比：可用版本依赖 glibc 的 `libc.so.6`、`ld-linux-aarch64.so.1`，并带有指向 Winlator rootfs 的 interpreter；失败版依赖 Android/Bionic 的 `libc.so`、`libm.so`、`libdl.so`，没有对应 RUNPATH。Winlator 是无 proot 的 glibc rootfs，Bionic 版本在 `LD_LIBRARY_PATH` 中命中了 GNU ld script 文本，`2f2a2047` 正是 `/* G` 的文本开头，不是 ELF 文件头。
2. **修正构建目标并迁移环境。** Windows 没有 `aarch64-linux-gnu-gcc`，因此把编译移到 WSL Ubuntu，使用 `ANDROID_GLIBC`/`aarch64-linux-gnu-gcc`，将 interpreter 指向 `<files>/rootfs/lib/ld-linux-aarch64.so.1`。静态检查显示 NEEDED、interpreter、RUNPATH、固定加载地址和 GLIBC 符号均符合预期，但真机仍以 exit 139、SIGSEGV 闪退，且 `BOX64_LOG/SHOWSEGV/SHOWBT` 都来不及输出。
3. **用“能跑的官方产物 vs 崩溃产物”做差分。** 继续逐项比较 ELF program headers 和打包脚本后，发现自定义步骤额外执行了 `patchelf --set-rpath` 和 `strip`。Box64 是非 PIE、固定加载地址 `0x34800000` 的特殊可执行文件；事后改 rpath 会重写 program headers/`.dynamic`，strip 也破坏了与官方构建一致的布局，导致动态链接器在 `main()` 之前就崩溃。
4. **形成最小修复并回归。** 采用上游 v0.4.3-4 + glibc 交叉编译；只设置 interpreter，不设置 rpath、不 strip；按原始目录结构重新制作 `box64-0.4.3.tzst`，更新 `DefaultVersion.BOX64`，重编 APK。构建日志确认 ELF 为 glibc NEEDED、rootfs interpreter 和 `LOAD 0x34800000`；真机正常进入桌面并启动星露谷，升级闭环完成。

### 最终根因与解决方案

- **根因一（首版）：** 编译平台错选 Android/Bionic，和 Winlator 的 glibc rootfs ABI 不匹配。
- **根因二（修正 ABI 后）：** 对非 PIE、固定地址 Box64 事后执行 `--set-rpath` + `strip`，破坏加载布局。
- **解决：** 目标 ABI 与 rootfs 一致；严格复刻官方打包配方，只改 interpreter；以可运行版本做 ELF 差分；保留 0.4.3 可回退版本。
- **验证：** 真机进入桌面并启动星露谷；后续项目2将默认版本推进到 0.4.5-dev，同时保留 0.4.3 回退，不影响本卡点结论。

### 可迁移经验

“能编译、能安装”不等于“能加载”。对底层二进制应先核对 libc/ABI、interpreter、PIE/固定地址和 program headers，再做真机验证；对于 main 前无输出的 SIGSEGV，优先检查加载器和打包步骤。

## 详细总结二：项目3触屏键盘失效卡点

### 背景与现象

G3-P0 首轮真机测试中，Dave the Diver 和星露谷都能运行，但触屏 D-pad 的 `W/S/A/D` 按钮无反应。问题跨两个游戏复现，初始表现像“游戏不接收按键”；同时首份性能 CSV 只有表头，不能用来推断帧率。

### 完整排查链

1. **先做跨游戏和输入日志观测。** 先验证“一个按钮绑定四个方向导致相互抵消”的假设，结果两款游戏都失败，否定了单个游戏配置问题。随后加入 `InputEventLogger`，记录绑定、XServer 注入、键盘去重、窗口 map/focus、目标窗口和静默丢弃原因。
2. **排除 Android/XServer 前段。** G3-P0-B 证明 X11 焦点、事件订阅和 enabled 状态正常；按键 press/release 均已发送且 drop=0。G3-P0-C 手动 `bringToFront()` 仍无效，排除前台窗口同步。G3-P0-D 又验证 WinHandler `VK_W` 直通：握手、排队和 UDP `sent=true` 全部正常，仍无响应。
3. **把观测点推进到 Wine 消费层。** G3-P0-E 增加标准 `FocusIn/FocusOut` 后仍失败；G3-P0-F/G 自动捕获 Wine trace，确认 `X11DRV_KeyEvent`、keysym `a`、vkey `0x41` 和 `X11DRV_send_keyboard_input` 都已执行，但扫描码是错误的 `0x78`。初始化日志显示 keycode 38 被 XKB 解析为 `NoSymbol`，随后分配备用扫描码。
4. **修正 X11 核心映射，再定位剩余缺口。** G3-P0-H 为全部 keycode 提供两组 keysym，修正 reply length、起始索引和写入数量；真机确认映射回复完整，但仍为 `NoSymbol/scan 0x78`。这把根因进一步收窄到 Wine 通过 XKB API 读取布局，而当前 XServer 未注册 XKEYBOARD 扩展。
5. **采用窄兼容层并交叉验证。** G3-P0-I 新增 x86_64 `libwinlator-xkb-core.so`，仅实现运行时所需的 XKB 核心函数，通过 `BOX64_LD_PRELOAD` 注入 guest；函数级测试退出码为 0，库大小 3,024 bytes。真机日志中 `A` 恢复标准扫描码 `0x1e`，Dave/星露谷均出现有效按键响应和 Raw Input，输入闭环完成。
6. **处理回归副作用。** G3-P1 性能 HUD 后续把根视图设为全屏 long-clickable，导致鼠标触摸被 HUD 提前消费。G3-P2 只把长按监听移到可见 FPS 面板，恢复触摸板事件下传；这说明修复后仍需做跨功能回归。

### 最终根因与解决方案

- **根因：** XServer 的 `GetKeyboardMapping` 数据虽已发送，Wine 读取 XKB 布局时因缺少 XKEYBOARD 扩展得到 `NoSymbol`，将标准按键映射为备用扫描码 `0x78`，游戏因此不识别。
- **解决：** 先用日志逐层排除绑定、焦点、事件丢弃、WinHandler 和 Wine 消费，再修正核心映射并增加客体侧 x86_64 XKB fallback；只补缺失函数，不改游戏文件或通用 Wine 行为。
- **验证：** `A/W/S/D` 获得标准扫描码，Dave 和星露谷真机输入均有效；随后把 HUD 触摸监听收窄到 FPS 面板，鼠标回归通过。

### 可迁移经验

输入问题不能只看“按钮有没有发出”。应沿 Android → XServer → WinHandler → Wine → XKB → Windows Raw Input 建立可观测链路，每轮只改一个层级，并用跨游戏复现、正反向日志和最终用户行为三重证据闭环。

- G3-P0 首轮黑屏/空 CSV 与跨游戏输入复现：`docs/项目3-Dave-the-Diver启动故障修复计划与执行记录.md:647-667`。

### 左栏：项目2｜Box64 升级后容器秒退

**现象**

0.4.0 → 0.4.3：APK 可安装，容器立即闪退；先见 `bad ELF magic`，改 ABI 后仍 exit 139、main 前无输出。

**定位**

① `readelf`：Bionic 产物与 glibc rootfs 不匹配；
② WSL 改用 glibc 后仍崩；
③ 与官方可运行 ELF 差分，锁定多余 `patchelf --set-rpath` + `strip` 破坏非 PIE 固定地址 `0x34800000`。

**解决 / 验证**

`ANDROID_GLIBC + aarch64-linux-gnu-gcc`；只设 interpreter，不设 rpath、不 strip；重打包 tzst。真机正常进桌面并启动星露谷。

### 右栏：项目3｜触屏键盘跨游戏无响应

**现象**

G3-P0 首轮中，Dave 与星露谷都能运行，但触屏 D-pad 的 `W/S/A/D` 同时无响应；跨游戏复现，首先排除单个游戏配置问题。

**定位**

逐层日志确认：按键绑定、X11 焦点、press/release、WinHandler 握手和 UDP `sent=true` 均正常，drop=0；问题已到达 Wine 消费层。Wine 收到 `vkey=0x41`，但 keycode 38 被 XKB 解析为 `NoSymbol`，最终扫描码错误地变成 `0x78`。修正 `GetKeyboardMapping` 后仍失败，进一步确认 XServer 缺少 XKEYBOARD 扩展。

**解决 / 验证**

先修正核心映射的长度、索引和容量，再增加仅 3,024 bytes 的 x86_64 XKB fallback，通过 `BOX64_LD_PRELOAD` 注入 guest。标准 `A` 扫描码从 `0x78` 恢复为 `0x1e`，`W/S/D` 也恢复正常；Dave、星露谷均确认实际响应。后续将 HUD 全屏长按监听移到 FPS 面板，鼠标回归通过。

### 底部方法论

**共同方法：先建立可运行基线 → 用日志把故障定位到具体层 → 每轮只改变一个变量 → 采用最小修复 → 以真机行为和反向证据交叉验证。**
